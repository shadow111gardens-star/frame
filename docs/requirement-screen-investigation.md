# REQUIREMENT_SCREEN investigation — 2026-10-12

## What the original error proves

The original sole `REQUIREMENT_SCREEN` throw was in `enforceScreenRequirements`, called by `planDesign` before plan approval, screen-ID binding or draft generation. Its condition compared each analysis-derived required name with planner names using lowercase only. Whitespace remained significant. A failure therefore meant a planning name was missing or mismatched, not that the rendered/generated app had necessarily omitted it. Planning failures bypassed the existing draft/review repair function.

The original Flowspace analysis/planning response for the reported failure is not stored locally, and the old diagnostic did not identify the name. It cannot be reconstructed from the generic 502. No specific historical missing screen is assumed.

The supplied exact prompt is an isolated public fixture in `tests/flowspacePrompt.txt`; it is not imported into the runtime UI. A controlled pre-change run completed analysis, planning, draft and review with Dashboard, Projects Listing, Project Details and Team Members. Updated live checks also returned 200 with all four screens. One intermediate live run needed the existing targeted navigation repair and succeeded afterward; the final run retained all four stable requirement IDs across approved plan, draft and review without repair. Records are under ignored `artifacts/screen-requirements/flowspace-*.json`. These are new reproductions, not recovery of the historical failing response. They verify server schema/plan/navigation validation, not browser-rendered visual quality.

## Confirmed defects and changes

- Case-only comparison rejected harmless whitespace variants. Later exact-name journey/planned-design checks used different matching rules. One shared key now trims/collapses whitespace and folds case; punctuation and different words remain distinct. Canonical user titles are restored only on a matching identity, not through fuzzy matching.
- Analysis used unrestricted substring evidence. A model-returned `Project Detail` could be accepted inside `Project Details`, and `Pro` inside `project`, creating requirements the prompt never named. Full phrase boundaries now exclude these. Conservative explicit-title lists and positively requested page/screen phrases recover names independently of omitted/shortened analysis. Quoted literal titles retain their wording; an unquoted grammatical `page`/`screen` descriptor is kept as content evidence rather than becoming a second title. Website sections, negative requests and examples do not become automatic screens.
- Genuine missing planning screens had no recovery. One `planning-repair` call now receives precise ID, expectedName and original requiredContent diagnostics. The merge adds only the missing screen specifications and necessary associated journey entries/edges, preserving valid existing specifications, tokens and links. All original schema/count/requirement/journey checks run again. A failed attempt returns an error rather than looping.
- Draft relationship validation could fail on a link to a missing destination before diagnosing the missing screen. Presence/identity validation now runs first. The existing targeted repair can restore the destination while preserving the source screen and its existing links; it can add necessary missing incoming actions using the existing guarded navigation repair. Unrelated or incorrectly named additions are ignored and the complete merged design is revalidated.

Fresh named requirements reserve IDs from their normalized keys before planning; valid preexisting internal plan IDs remain authoritative. Approved `requiredScreens` binds each key/name/content to the actual screen ID. This contract goes through the existing draft, review and repair payloads. Existing projects, modification IDs, the editable JSON schema, tokens and the navigation contract are unchanged.

Planning repair has its own one-attempt bound and does not consume the already separate draft/review allowances. All calls still use the configured Gemini model, adapter, cancellation and overall deadline. Planning repair adds model usage only when needed; no provider, paid service, queue or infrastructure was added. Detailed missing-screen evidence goes to the caller and repair request, not shared server logs.

## Firestore investigation

The installed Firestore transport's `FetchXmlHttp.abort` calls `AbortController.abort()` and catches reader cancellation. The previously traced path is StreamBridge close → WebChannel close/cancel → fetch transport cleanup; internal snapshot listeners also support server document/query reads. FRAME's project/auth code does not create a Firestore AbortController, terminate its singleton on unmount, or globally suppress unhandled rejections. Existing UID guards and bounded returned-AbortError handling remain intact and tested. No additional lifecycle defect was confirmed. An unexpected production SDK-internal unhandled rejection remains unreproduced; this does not classify every AbortError as harmless. Firebase files and security rules were not changed.

## Verification and limits

Regressions cover the exact Flowspace requirement extraction, singular/truncated phantom titles, case/whitespace normalization, literal titles, exclusions/sections/examples, stable IDs, genuine missing planning screens, bounded failed planning repair, destination restoration, preservation of existing screens/links, and actual HTTP-stage/response behavior. Full-suite verification includes existing navigation, Firebase cancellation/authentication, persistence and client design-preservation tests. The live harness requires explicit `--live` and uses only the existing configured service.

Local extraction remains conservative; broader semantic interpretation still uses Gemini. Missing-screen repair cannot conceal extra screens, count conflicts, invalid components, token conflicts or broken navigation. These still fail original validation. Required content is supplied to the model and repair stage; structural checks do not certify semantic completeness or subjective design quality.

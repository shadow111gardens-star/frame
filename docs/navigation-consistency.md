# Navigation consistency investigation (2026-10-12)

The creative planning response describes `journey.edges` by exact screen names and an action. Previously, the first draft request had no reserved screen IDs or resolved edge contract. IDs were chosen by the draft and resolved only for review/repair. Components, the schema and the renderer use `targetScreenId`, not destination names. Tests reproduced the missing pre-generation ID binding, missing detailed diagnostics, and a repair rewriting valid components on its source screen. These are confirmed code defects; the particular latest live failing Gemini response was not available and was not reproduced against the paid API.

After plan validation, `approvePlanNavigation` reserves screen IDs and binds each existing approved edge to `fromScreenId` and `toScreenId`. Planning's model-facing schema remains name-based; FRAME supplies IDs afterward. The same `resolvedNavigation` records accompany initial generation, review and repair. Generation must keep reserved IDs, and validation checks them. Only explicitly approved edges are required; no return edge or peer tab is inferred. Imported/current projects and modification screen IDs are unchanged.

The editable JSON schema still uses existing screen/component IDs and `targetScreenId`. `GeneratedSurface` handles clicks on wrappers, including Text and Card surfaces, not just native buttons. Browser regression checks exercise both. `isNavigationAction` permits supported clickable surfaces, checks hidden/zero-opacity ancestors and excludes decorative components, Input/Search, and same-page anchors that would intercept screen navigation.

Failures retain edge indexes and supply `missingNavigation` with source/destination names, IDs and the action. This detailed evidence goes to the existing repair request and caller response. Shared server logs omit user-authored names/action labels. Repairs preserve working links, valid source-screen components, unrelated screens and tokens. They may change a missing action's link/label or append a necessary visible action subtree; they cannot redirect working links, reveal hidden subtrees or recompose the source screen. Merged results pass the original schema, relationship and plan validation. Existing bounded per-stage accounting remains; unsuccessful repair returns HTTP 502 with its stage and diagnostic, without an app result or another validation loop.

## Firebase investigation

Installed Firebase Auth code in `node_modules/.vite/deps/firebase_auth.js`, `pollUserCancellation`, reads the popup's `window.closed`. FRAME delegates sign-in to `signInWithPopup` and does not set COOP/COEP headers in its Node or Vite configuration. The earlier browser investigation recorded Google's report-only COOP warning and successful opening/handled closure of the sign-in popup, not completed real authentication. A warning alone is insufficient to diagnose a blocked OAuth handshake. Successful real Google login and deployment headers were not reverified here; no auth/header changes or console suppression were justified. Official flow: https://firebase.google.com/docs/auth/web/google-signin.

Installed Firestore code confirms `StreamBridge.close` invokes WebChannel close; fetch transport cleanup calls `AbortController.abort()` without a reason. Reader cancellation and read failures already have SDK catches. Server document/query reads use transient snapshot listeners internally. FRAME uses a singleton Firestore instance and does not call SDK termination or issue its own Firestore AbortController on component cleanup. Its existing operation wrapper distinguishes account changes, retries a returned transport AbortError once for the same owner and exposes repeated interruption or permission failures. Existing tests cover synchronous save failures, deduplicated/superseded loads, stale-account failures and cleanup. No additional lifecycle defect was confirmed, so these fixes and security rules were preserved. The production SDK-internal rejection leak remains unreproduced. Listener guidance: https://firebase.google.com/docs/firestore/query-data/listen.
